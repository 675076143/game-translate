# 从游戏画面到中文字幕：用 Rust 构建本地实时 OCR 翻译器

玩没有中文支持的游戏时，传统截图翻译总会打断操作：截图、切窗口、粘贴、等待，然后回到游戏。对对白密集的 RPG 来说，这种流程很快就会从“偶尔麻烦”变成“根本不想看剧情”。

`game-translate` 想解决的就是这个具体问题：在 Hyprland 上选择一次游戏窗口，之后自动识别新出现的英文对白，并在旁边的终端里显示简体中文。核心程序使用 Rust 编写，截图、OCR、缓存和大模型翻译都在本机完成。

项目地址：<https://github.com/675076143/game-translate>

## 最小可用链路

最初的目标很简单：

```text
选区 → 截图 → Tesseract → 翻译 → 输出
```

这条链路很快就能跑通，但“能翻译一张截图”和“可以持续开着玩游戏”是两件完全不同的事。真正影响体验的不是某一次 OCR 是否成功，而是程序能否判断什么时候该识别、能否跟住游戏窗口、能否避免重复翻译，以及运行几小时后是否仍然稳定。

因此现在的完整流程变成了：

```text
Hyprland 窗口跟踪
  → Wayland 内存捕获
  → 画面变化与稳定检测
  → RapidOCR 文字检测与识别
  → 坐标排序、文本块组合与 UI 过滤
  → 候选稳定确认
  → 近似去重
  → 术语模板 / 缓存 / Ollama
  → 中英双语输出
```

每一层只做一件事，模块之间传递的也只是窗口几何、图像、OCR 结果或翻译任务。这种拆分让问题可以被单独复现，而不用在一条巨大的循环里猜测。

## 为什么要跟踪程序窗口

只记录一个屏幕矩形并不可靠。平铺布局变化、窗口缩放或工作区切换以后，同一个坐标可能属于终端、浏览器甚至聊天窗口。继续截图不仅识别错误，还可能把无关内容送去翻译。

窗口模式会通过 Hyprland IPC 获取候选窗口，再让用户点击选择。程序保存的是窗口地址以及字幕区域相对于窗口的偏移，而不是一组永远不变的绝对坐标。

运行期间每 500ms 刷新一次窗口几何：

- 窗口移动或缩放时更新捕获区域；
- 窗口不在活动工作区时暂停识别；
- 窗口重新可见后继续运行；
- 相同位置被另一个程序占用时不会误绑定。

这是项目从“截图脚本”变成“可长期运行工具”的关键一步。

## 不要对每一帧做 OCR

游戏通常以几十或上百帧刷新，但对白只在少数时刻改变。每帧运行 OCR 既浪费 CPU，也会不断读到打字机动画的半句话。

程序会对图像做稀疏亮度采样，通过状态机判断画面正在变化还是已经稳定。检测到稳定候选后执行 OCR，再等待下一次结果确认文字没有继续增长。这样可以过滤大部分动画帧，并避免把：

```text
Would you li...
```

当成最终对白送去翻译。

变化检测仍然只关注更可能出现文字的区域，避免中央角色动画持续触发 OCR；真正识别时则由文字检测模型在游戏窗口内寻找文字框。这样既控制了调用频率，也不再假设对白一定出现在某个固定坐标。

## 为什么最终换掉 Tesseract

实际调试中出现过一个很典型的错误：画面明明是：

```text
We restore your tired Pokemon to full health.
```

最初使用的 Tesseract 却稳定输出：

```text
ke restore your tired Pokémon o Tull health.
```

这不是随机抖动。同一张 Wayland 捕获帧在原始尺寸下会持续得到相同错误。2× 最近邻放大、灰度化、Otsu 阈值、颜色通道提取和更精确的裁剪都能改善某些样本，但总会让另一些字体退化。

真正促成替换的是物品说明：

```text
A splicer that fuses the DNA of any two Pokémon into a single entirely new Pokémon.
```

Tesseract 会稳定产生 `ONH`、`Polcemon`、`=ingle` 等错误。继续增加游戏专用阈值和裁剪，只会得到越来越脆弱的规则。

现在改用 RapidOCR 的 PP-OCRv6 模型。它先检测文字框，再识别每个文字块，并由一个常驻 worker 保持模型只加载一次。Rust 与 worker 使用长度前缀 JSON 协议传递 PNG 和结构化结果；没有为旧 Tesseract 保留兼容路径。

同一张失败截图的新结果是：

```text
A splicer that fuses the DNA of any two Pokémon into a single entirely new Pokémon.
```

实测 OCR 通常耗时约 400～740ms。更重要的是，《Bayonetta》的衬线字体也能沿用同一条链路，不需要增加另一套游戏规则。

检测模型会返回多个文字框，因此“识别出字”之后还有一步：按纵坐标合并同一行，再按间距和水平重叠组成连续文本块，最后过滤短 UI 标签、全大写按钮、URL 和低置信结果。无文字画面是正常状态，`text detection result is empty` 不应显示给玩家。

## 本地翻译与两级缓存

OCR 后的文本不会发送到云端。翻译线程调用本机 Ollama 中的 `qwen3:4b-instruct`，提示词要求使用简体中文、宝可梦官方术语，并纠正明显的 OCR 错字。

翻译按下面的顺序查找：

1. 已知战斗模板；
2. 256 条内存缓存；
3. SSD 上的 JSON Lines 文件缓存；
4. 本地 Qwen 模型。

宝可梦中心、商店和战斗系统会频繁重复对白。缓存命中后不需要模型推理，跨重启也能立即输出。内存缓存保持有界，文件缓存则可以利用 SSD 保存更多历史结果。

翻译运行在独立工作线程中。高置信且完整的句子可以提前发起推理；如果确认阶段发现画面已经变化，旧结果会被标记为过期而不再输出。这让模型延迟不会阻塞截图循环。

## 一次真实的 OOM 排查

持续截图版本曾经导致 Hyprland 被内核 OOM killer 终止。表面上看，最可疑的是常驻的大语言模型，但系统日志显示不断增长的是 compositor 的共享内存，而不是 Ollama 进程。

问题来自 Wayland 捕获对象的生命周期：连续创建的帧没有完整销毁，compositor 一直持有共享缓冲区。项目因此固定使用 wlroots screencopy 路径，并在 vendored `libwayshot` 中确保成功和失败路径都会销毁 frame、session 和 source 对象。

1000 帧压力测试中，共享内存会在捕获期间短暂增加，并在结束后回到起始水平。这个案例也提醒我们：发生 OOM 时，进程 RSS 最大的不一定是真正的泄漏源；必须结合内核日志和共享内存指标判断所有权。

## 为什么选择 Rust

这个项目的瓶颈并不是“Rust 比脚本语言快多少”，而是持续运行时需要可控的资源生命周期、清晰的并发边界和稳定的内存占用。

Rust 在这里带来的实际收益包括：

- Wayland 对象和图像缓冲区的生命周期更容易审计；
- OCR 与翻译线程之间使用明确的消息通道；
- 状态机、窗口几何和缓存都可以写成小型单元测试；
- 截图、窗口跟踪、稳定检测、缓存和并发边界都留在 Rust 主进程；
- 长时间运行时更容易保持可预测的内存行为。

成熟组件仍然优先：截图使用 `libwayshot`，OCR 使用 RapidOCR、PP-OCRv6 和 ONNX Runtime，翻译使用 Ollama。OCR worker 安装在独立的 `uv` 虚拟环境中，Rust 负责进程生命周期和稳定的二进制协议，而不是重新实现文字检测与神经网络推理。

## 现在能做什么

当前版本面向 Hyprland、英文到简体中文以及终端输出，已在《Pokémon Infinite Fusion》和《Bayonetta》中实测。它提供窗口跟踪、区域模式、场景文字检测、多行文本块组合、UI 过滤、本地翻译、两级缓存、日志和捕获压力测试。

安装与使用方法见项目 [README](../../README.md)。如果你也在 Wayland 下玩没有中文支持的游戏，欢迎尝试、提交实际失败截图或贡献新的 OCR 回归用例。
